## 摘要

**最严重的 3 个问题（P0）**

1. **Windows 一键装 VB-CABLE 后，系统默认播放/录音设备很可能被换成虚拟线，而且应用不检查、不恢复。** VB-Audio 官方手册原话：Windows 10 起"最后安装的音频驱动可能被自动设为默认设备……电脑所有声音都进 CABLE Input（你什么都听不到了）"。结果是：Teams/Zoom/浏览器/音乐全部没声音；本应用自己的"系统默认麦克风"变成 CABLE Output、"系统默认输出"变成 CABLE Input，于是对方会在会议里听到自己发言的中文译音，"原声进会议"开着时还会形成数字回授（啸叫）。（`virtual-audio.ts:96-127`、`DriverInstaller.tsx:15-38`、`engine.ts:110-119,165,169-174`）
2. **iPhone 用局域网二维码加入现场房间，大概率连不上。** 房间用自签名证书的 HTTPS + `wss://`。多方资料（Cockpit 官方文档、WebKit bug、websockify 文档）都说：iOS Safari 的 WebSocket 栈不接受自签名证书，即使用户在页面上点了"访问此网站"也不行。网页上只会无限显示"连接中断，正在重连…"，没有任何提示让用户改用公网链接。iPhone 只能走网页这条路，所以这个问题等于 iPhone 用不了。（`room-host.ts:163-170`、`cert.ts:30-60`、`RoomClient.tsx:137-139,193-198`）**需真机验证**，但风险很高。
3. **鸿蒙 NEXT 手机打开官网会被引导去下载"Linux AppImage"。** 鸿蒙 NEXT 的 UA 里没有 `Android`/`iPhone`（华为官方格式是 `Mozilla/5.0 (Phone; OpenHarmony 5.0; …) … ArkWeb/…`），`site/index.html:162-196` 的判断会落到最后的"下载 Linux 版"分支。这一条严格说是 P1（不会弄坏别的软件），但这类用户在入口处就被挡住了，建议和 P0 一起修。

**主要的 P1 问题**

- 字幕悬浮窗默认放在屏幕底部中央（宽 70%、高 190px），层级是 `screen-saver`，还会盖在全屏应用上，而且默认**不穿透点击**。Teams、Zoom、腾讯会议、飞书的静音/离开/共享按钮正好在这个位置，会被挡住点不到。
- macOS 安装 BlackHole 时，应用主动重启 `coreaudiod`，整台 Mac 的声音会中断几秒，正在进行的通话会断音。BlackHole 自己的安装包并不会这样做。
- 按照引导，用户把 Teams/飞书等的麦克风（以及扬声器）改成虚拟设备后，**不开本应用时这些会议软件就没声音**。应用从不提醒用户改回来，卸载也不会提醒。
- 没有阻止用户把"虚拟麦克风的另一端"（CABLE Output / BlackHole 2ch）选成自己的麦克风或"会议声音"，选了就会自激回授，或者把自己的译音再翻译一遍。
- 本机 AI（llama.cpp，线程数 = 逻辑核数的一半，2–6 个）加本机识别（每个方向 2+1 线程）都是**普通优先级**，没有降低优先级。低配笔记本上会和 Teams/Zoom 抢 CPU。
- 房间服务监听 `0.0.0.0`：Windows 会弹防火墙询问。如果用户点了取消、没有管理员权限，或者当前网络是"公用网络"，手机就扫不进来，而应用完全不提示。
- macOS 版是 ad-hoc 签名，**每次升级签名都会变**：麦克风和"录屏与系统录音"授权会失效，或者设置里显示已开但实际不生效，"系统声音"模式会采不到声音。
- Windows 上几 GB 的模型（识别约 0.6 GB，AI 1.1 GB 或 4.6 GB，离线翻译 138 MB，cloudflared）全放在 `%APPDATA%\Roaming`。企业漫游配置文件会在每次登录/注销时同步，拖慢登录、撑爆配额。
- 安卓 App 没有处理切到后台：麦克风、云端识别连接、通话音频模式都继续保持。后台的麦克风只能录到静音，却还在按秒计费，同时耗电，还可能让其他 App 的声音变成"通话音质"或走听筒。
- iPhone 打开静音拨片时，Web Audio 播放的译音会被系统静音（默认 `ambient` 会话）。代码里没有设置 `navigator.audioSession.type = 'playback'`，用户只会觉得"听不到"。
- 中国用户习惯用微信扫码。房间二维码是自签名证书的 IP 地址链接，微信内置浏览器无法"继续访问"（需真机验证）。
- **Chrome 插件**：在 12 个会议域名的所有 frame 里，`getUserMedia` 被**一直接管**（不是只在同传时）。真实麦克风先经过插件自己建的 AudioContext 再交给会议页面。如果这个 AudioContext 因自动播放策略处于 suspended 状态，会议拿到的就是**无声麦克风**，直到用户在页面上点一下。即使用户根本没在用同传也会这样。
- 口音校准录音中途离开页面（不点"取消"/"读完了"）时，麦克风不会释放：系统麦克风指示灯一直亮，蓝牙耳机被拖进通话模式，内存每小时约增长 0.7 GB。

**检查过、没有问题的地方**

- 代码从不修改系统默认音频设备。
- 没有开机自启、登录项、文件关联，也没有向系统注册协议（`mi-app://` 只在应用进程内注册）。
- 插件的 DNR 规则只作用于插件自己的 WebSocket（`tabIds:[-1]`）。
- 桌面桥只监听 127.0.0.1，不会触发防火墙。
- 在托盘空闲时没有轮询（电平每 250ms 一次的定时器只在会议中运行，设备变化靠事件，更新检查只在启动后查一次）。
- 会议结束、试音、声音复刻录音、设备列表探测都会正确释放麦克风。
- Windows 上 PowerShell 常驻进程和 cloudflared 会随应用退出被结束（libuv 作业对象 + stdin 关闭）。
- macOS `say` 的临时目录会被清理。
- 手机端不使用 SharedArrayBuffer、speechSynthesis、MediaRecorder；离线翻译 WASM 不需要线程和 SIMD。
- 安卓"保持亮屏"只用窗口 flag，不是 WakeLock。
- 房间网页在点击时解锁音频，符合 iOS 自动播放规则。
- 悬浮窗用 `showInactive()` 显示，不抢焦点。

## P0

### P0-1 Windows 安装 VB-CABLE 后默认设备被替换，应用不检测、不恢复，还默认使用"系统默认"设备
- **平台**：Windows 10/11（确认 + 厂商文档）
- **位置**：
  - `src/main/platform/virtual-audio.ts:112-119`：`Start-Process … VBCABLE_Setup_x64.exe -ArgumentList '-i','-h' -Verb RunAs -Wait`，静默安装。安装前没有记下默认设备，安装后也没有恢复。
  - `src/renderer/src/components/DriverInstaller.tsx:24-35`：装好后只把 CABLE Input 设为"虚拟麦克风"并播放测试音，没有检查 `enumerateDevices()` 里 `deviceId==='default'/'communications'` 那一项是不是变成了 CABLE。
  - `src/core/config/schema.ts:115-124`：`devices.mic=''`、`devices.headphones=''` 默认就是"系统默认"。
  - `src/renderer/src/audio/engine.ts:110-119`：`deviceId: cfg.mic ? exact : undefined`，也就是默认麦克风。
  - `engine.ts:165`：`makeSink(cfg.headphones || '')`，也就是默认输出。
  - `engine.ts:169-174`：麦克风 → `micToMeeting` → 虚拟麦克风（CABLE Input）。
  - `src/renderer/src/api.ts:57-61`：设备列表把 `default`/`communications` 两项过滤掉了，用户看不到"默认现在是谁"。
- **问题**：VB-Audio《VBCABLE_ReferenceManual》第 6 页 *Set VB-Cable as default device* 原文："With Windows 10 and higher, the last installed audio driver can be automatically set as default device … All PC Sound will come in VB-CABLE input (so you will not hear any sound anymore)." 论坛和微软问答上有大量同类报告。CABLE Output 也常被设成默认录音设备。
- **对用户和其他软件的影响**：
  1. 所有使用"默认设备"的软件（Teams 新版默认就是"默认设备"、浏览器、微信、音乐等）都没声音，或者麦克风只收到虚拟线里的声音。
  2. 本应用的"系统默认输出"会把给用户听的**中文译音送进 CABLE Input，也就是送进会议麦克风**：对方会听到自己发言的中文译音，而用户自己什么都听不到。
  3. "系统默认麦克风"变成 CABLE Output，再经过 `micToMeeting` 回到 CABLE Input，形成回路。打开"原声进会议"（增益 1）时就是数字啸叫；即使增益为 0，本应用也会把自己的西语译音当成"我说的中文"去识别。
  4. 用户通常不会想到是这次安装造成的，只会觉得"装了这个软件以后电脑没声音了"。
- **建议修法**：
  - 安装前用 PowerShell 读取并保存当前默认播放、录音、通信设备的 ID，安装后恢复。可以用内嵌 C# 调用 `IPolicyConfig`；如果不想用 Add-Type，也可以只读不写，改为提示用户。
  - 最低限度：安装完成和每次开会前，在渲染层检查 `enumerateDevices()` 中 `default`/`communications` 项的 label。如果匹配 `/CABLE|VB-Audio|BlackHole/`，弹出阻断式提示，并提供"打开声音设置"按钮（`ms-settings:sound` 或 `mmsys.cpl`）。
  - 首次引导时把"麦克风"和"耳机"固定成具体的物理设备 ID，不再依赖 `''`。
  - 引擎层兜底：`mic` 或 `headphones` 解析出来是虚拟设备时拒绝启动对应的通路。
- **能否自动测试**：
  - 部分可以。默认设备是虚拟线时的拦截逻辑，可以在 vitest/Playwright 里伪造 `enumerateDevices` 来测。
  - 安装前后默认设备是否被保持，需要 Windows 实机或自托管 runner：装 VB-CABLE 后用 `Get-AudioDevice` / Core Audio 查询默认设备。GitHub 托管的 Windows runner 没有音频端点，不太适合。

### P0-2（需真机验证）iPhone 通过局域网链接加入房间时 WebSocket（wss + 自签名证书）大概率失败，且无回退、无提示
- **平台**：iOS / iPadOS Safari（以及 Apple 芯片 Mac 上的 Safari）
- **位置**：
  - `src/main/room/room-host.ts:163-170`：非 insecure 模式用自签名证书起 HTTPS。
  - `src/main/room/cert.ts:30-60`：`selfsigned` 生成证书，CN 为 `meeting-interpreter.local`，SAN 为局域网 IP。
  - `src/renderer/src/room/RoomClient.tsx:137-139`：`new WebSocket('wss://…/ws')`。
  - `RoomClient.tsx:193-198`：断开后指数退避，无限重连。
  - `Guide.tsx:84`、`README.md:120`：只教用户在 iPhone 上点"显示详细信息 → 访问此网站"。
- **问题**：Cockpit 官方文档写明 "Safari's default WebSocket framework on iOS, iPadOS, and ARM-based Macs does not support the WebSocket Secure sessions … when using a self-signed or otherwise invalid certificate, even when they are manually marked as trusted"。WebKit bug 41419、websockify 文档、Apple 开发者论坛（含 iOS 26 的帖子）都有同类报告：页面上点的"继续访问"不会带到 `wss://`。
- **影响**：页面能打开（HTML 走 HTTPS 例外），但 WebSocket 一直连不上，界面只显示"Connection lost, reconnecting…"。iPhone 用户只能用网页加入，等于完全用不了；公网链接（trycloudflare，证书有效）可能能用，但页面不会提示去用它。
- **建议修法**：
  1. 真机确认（iOS 17 / 18 / 26 各一台）。
  2. 房间页检测到 iOS 且 wss 连续失败约 2 次时，提示"请改用公网链接"，并在桌面端房间页对 iPhone 优先展示公网二维码。
  3. 给局域网链路加一个不依赖 WebSocket 的回退：HTTPS 长轮询，或 `fetch` 上行 + SSE 下行。普通 HTTPS 请求能不能沿用页面例外，同样需要真机验证。
  4. 长期方案：用公信证书（例如自有域名的通配证书配合 IP 映射域名），或者生成本地 CA 引导用户安装（体验差）。
- **能否自动测试**：Playwright 的 WebKit **测不出来**（网络栈不同，而且现有测试用了 `ignoreHTTPSErrors`，见 `e2e/room.spec.ts:23`）。需要真机，或 BrowserStack/Sauce 等真 iOS 设备云。回退逻辑本身（连续失败后切换）可以在 Playwright 里通过让 WS 端点返回 403 来测。

### P0-3（严格说是 P1，但在入口处挡住用户）鸿蒙 NEXT 在官网被识别成 Linux
- **平台**：HarmonyOS NEXT（5.x / 6.x）浏览器
- **位置**：`site/index.html:162`（`isPhone` 只认 `iPhone|iPad|iPod|Android`），`site/index.html:196` 兜底为"下载 Linux 版 AppImage"。
- **问题**：华为官方文档里 ArkWeb 默认 UA 的格式是 `Mozilla/5.0 (Phone; OpenHarmony 5.0; HarmonyOS 5.0) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/114.0.0.0 Safari/537.36 ArkWeb/4.1.6.1 Mobile`，其中没有 `Android`。API 15 起连 HarmonyOS 字段都去掉了。
- **影响**：鸿蒙 NEXT 用户（只能用浏览器加入房间）会被引导下载 Linux 桌面程序，看不到"扫码加入"的说明。
- **建议修法**：把 `/OpenHarmony|HarmonyOS|ArkWeb/i` 归入手机分支，走和 iPhone 相同的"扫码就能用"说明；同时用 `/Mobile/i` 兜底。
- **能否自动测试**：可以。用 Playwright 设置自定义 UA 打开 `site/index.html`，断言主按钮文案。

## P1

### P1-1 字幕悬浮窗默认挡住会议软件底部控制栏；层级最高、覆盖全屏应用、默认不穿透点击
- **平台**：macOS、Windows
- **位置**：
  - `src/main/windows.ts:79-86`：底部居中，宽 = min(1000, 工作区宽度的 70%)，高 190，距底 40px。
  - `windows.ts:106`：`setAlwaysOnTop(true,'screen-saver')`。
  - `windows.ts:107`：`setVisibleOnAllWorkspaces(true,{visibleOnFullScreen:true})`。
  - `windows.ts:93`：`focusable:true`。
  - `schema.ts:155`：`overlay.enabled:true, clickThrough:false`。
  - `src/main/index.ts:355`：`meeting.start` 后自动 `showOverlay()`。
  - `overlay/main.tsx:41-55`：整块是不透明背景加 drag 区域。
- **问题和影响**：Teams、Zoom、腾讯会议、飞书最大化或全屏时，静音/挂断/共享按钮都在底部中间，正好被 190px 高的字幕条挡住，而且这个区域收不到点击。macOS 的 `screen-saver` 层级（约 1000）高于 Zoom 共享工具条、通知横幅、菜单等，会议软件全屏时也照样盖在上面。共享屏幕时字幕被 contentProtection 隐藏，但本地照样挡着。用户在关键时刻点不到"静音"，属于直接干扰其他软件。
- **建议修法**：
  - 默认位置避开底部 120px 左右（放在会议窗口区域靠上，或第一次运行时让用户拖放并记住位置）。
  - 默认只有字幕文字和按钮区域响应鼠标，其余透明区域穿透。可以用 `setIgnoreMouseEvents(true,{forward:true})` 加 hover 切换，现在按钮区已经这样做了，推广到整个窗口。
  - macOS 改用 `'floating'` 或 `'pop-up-menu'` 层级，不要用 `'screen-saver'`。
  - 记住用户拖动后的位置。
- **能否自动测试**：可以。单元测试断言默认 bounds 不在工作区底部 N px 内、默认穿透；Playwright for Electron 读取 overlay 的 `getBounds()`。

### P1-2 macOS 安装 BlackHole 时强制重启 coreaudiod，整机断音
- **平台**：macOS
- **位置**：`src/main/platform/virtual-audio.ts:84`：`launchctl kickstart -kp system/com.apple.audio.coreaudiod || killall coreaudiod`。提示文字（第 77 行）只说"请输入电脑密码"，没有说会断音。
- **问题**：我解开了 BlackHole 0.7.1 安装包，它的 `postinstall` 只做 chown/chmod，不重启 coreaudiod，Distribution 里写的是 `onConclusion="RequireRestart"`。断音完全是本应用加的这一步造成的。
- **影响**：正在进行的 Teams/Zoom/浏览器通话会断音几秒；部分软件（DAW、OBS、某些 Electron 应用）要重启才能恢复；蓝牙耳机可能断开重连；系统默认输出偶尔会被重置。用户常常就是在开会前、会议软件已经打开时才去点"一键安装"。
- **建议修法**：安装前明确提示"安装过程会让电脑声音中断几秒，请先结束通话"，让用户确认。或者干脆不重启 coreaudiod，改为提示"装好后重启会议软件，必要时重启电脑"。还可以检测到会议软件在运行（`detectMeetingApps()`）时先警告。
- **能否自动测试**：可以做单元测试，断言脚本内容或"确认对话框必须先出现"。断音本身只能实机验证。

### P1-3 会议软件被改到虚拟设备以后，不开本应用时会议没有声音，应用从不提醒改回来
- **平台**：macOS、Windows
- **位置**：`src/renderer/src/content/guides.ts:14-18,24-27,33-37,45,…`（引导用户把 Teams/飞书/腾讯会议/Zoom/钉钉/企业微信的麦克风改成 CABLE Output / BlackHole 2ch，"虚拟扬声器"模式下扬声器也改成虚拟设备）。全仓库搜不到"改回 / 换回"之类的提示。
- **影响**：下次开会如果没开本应用（或者已经卸载），对方听不到用户说话（虚拟线里没有信号），用户也听不到对方（扬声器指向虚拟设备）。这是对其他软件的持续性破坏，而且很难排查。
- **建议修法**：
  - 会议结束、退出应用时提醒"不用同传时，请把会议软件的麦克风/扬声器改回原设备"，给出各软件的入口，并提供"不再提示"。
  - 卸载说明和官网也要写上。
  - 尽量推荐不需要改扬声器的"系统声音"模式。
  - 可以在引导里推荐会议软件里的"在会议中临时切换设备"（只对本场会议生效），不改全局设置。
- **能否自动测试**：提醒的显示逻辑可以用 Playwright 测。是否真的影响到会议软件不能自动测。

### P1-4 没有阻止把"虚拟麦克风的另一端"选成麦克风或会议声音，选了就会自激或循环翻译
- **平台**：macOS、Windows
- **位置**：
  - `src/renderer/src/pages/Settings.tsx:593-600`：麦克风下拉列出所有输入设备，包括 CABLE Output / BlackHole 2ch。
  - `Settings.tsx:625`：会议声音设备的下拉也一样。
  - `guides.ts:132-139`：`guessMeetingDevice` 只在"自动猜"时避开。
  - `engine.ts:169-174`：麦克风 → 虚拟麦克风的直通。
- **影响**：
  - 麦克风选成 CABLE Output 时形成回路：直通增益为 1（"原声进会议"/passthrough）就是数字啸叫，对方听到刺耳噪声；增益为 0 时，本应用会识别自己的西语译音并继续翻译。

  - 和 P0-1 叠加时，用户什么都没选也会掉进这个状态。
- **建议修法**：根据 `guessVirtualMic` 的标签规则，在保存设置和开会时拒绝"麦克风 = 虚拟麦克风的另一端"和"会议声音 = 虚拟麦克风的另一端"，并给出提示。引擎里也加一道保护：`micToMeeting` 只在麦克风不是虚拟设备时才连接。
- **能否自动测试**：可以。纯函数单元测试，加 Playwright 设置页测试（伪造设备列表）。

### P1-5 本机 AI / 本机识别以普通优先级、多线程运行，会和会议软件抢 CPU
- **平台**：macOS、Windows（尤其是 4 核/8 线程的轻薄本、8 GB 内存的 Mac）
- **位置**：
  - `src/main/index.ts:155`：`threads: Math.max(2, Math.min(6, Math.floor(cpus().length / 2)))`，8 个逻辑核就是 4 线程。
  - `src/main/providers/local-asr/recognizer.ts:186,192`：每个识别会话 2 线程，再加 VAD 1 线程，两个方向各一个 utilityProcess（`index.ts:202`）。
  - `index.ts:129-135`：`utilityProcess.fork` 没有降低优先级。
  - 全仓库没有 `os.setPriority`。
  - `local-ai/worker.ts:31`：`gpu:'auto'`，Apple 芯片上走 Metal，会和视频会议争 GPU。
- **影响**：本机 AI 加两路本机识别同时工作时，可能有 8–10 个满载线程，和 Teams/Zoom 的视频编解码、浏览器会议的渲染竞争：画面卡顿、对方看到我方视频掉帧、机器过热降频。会议软件的音频线程通常有 MMCSS / 实时优先级，一般不会断音，但整体体验会变差。另外：
  - 7B 模型（4.6 GB）没有内存检查（`model.ts:17`，`schema.ts:93` 默认 1.8B），8 GB 机器选了会大量换页，拖慢整机；
  - 模型在会后 10 分钟内仍占用内存（`local-ai/client.ts:95`）。
- **建议修法**：
  - fork 后调用 `os.setPriority(child.pid, os.constants.priority.PRIORITY_BELOW_NORMAL)`。Windows 上对应 BELOW_NORMAL_PRIORITY_CLASS，mac 上相当于 nice 10。
  - 线程数按物理核计算，上限 4。用电池时再降。
  - 7B 在内存小于 16 GB 时禁用或警告。
  - 会议结束时立即 `dispose()` AI worker。
- **能否自动测试**：部分可以。单元测试断言 fork 后设置了优先级、线程数计算正确。真实的 CPU 争用需要在 CI 的 Mac/Windows 机器上做性能基准（例如同时播放视频，统计掉帧）。

### P1-12 Chrome 插件一直接管会议网站的 getUserMedia；AudioContext 处于 suspended 时会议拿到无声麦克风
- **平台**：Chrome（所有安装了插件的用户，不管有没有开同传）
- **位置**：
  - `extension/manifest.json:59-81`：`page-mic.js` 注入 12 个会议域名，`all_frames:true`、`world:MAIN`、`document_start`。
  - `extension/src/page-mic.ts:125-134`：只要 `constraints.audio` 存在就 `hook()`。
  - `page-mic.ts:39-51`：首次 getUserMedia 时 `new AudioContext()`，在 suspended 状态下要等 pointerdown/keydown/touchstart 才 resume。
  - `page-mic.ts:72-92`：真实麦克风 → GainNode → `MediaStreamDestination`，返回给会议的是 destination 轨道。
- **问题**：Chrome 的自动播放策略下，文档在没有用户激活时创建的 AudioContext 会以 suspended 启动（媒体参与度高的网站例外）。suspended 时 destination 轨道输出全是静音。代码注释承认了这一点（第 46 行）。
- **影响**：
  - 用户从日历链接直接进入 Meet/Teams 网页版时，预览页的麦克风音量条可能不动（会议软件提示"检测不到麦克风"），直到用户点一下页面。

  - 即使是 running 状态，所有麦克风音频也都要多经过一次 WebAudio（增加约 10–40ms 延迟、重采样，见 P2-1）。
- **建议修法**（按优先级）：
  1. `hook()` 里如果 `ac.state !== 'running'`，直接返回原始 stream，不接管，并通知插件"需要点一下页面后重新选择麦克风"。
  2. 只在同传会话进行中（或用户为该站点打开开关）时才接管；同传开始时用 `RTCRtpSender.replaceTrack` 替换已经发送的轨道（hook `RTCPeerConnection.addTrack/addTransceiver` 记录 sender）。
  3. 非同传状态下 `pass` 直通不经过 WebAudio，直接返回原始轨道。
- **能否自动测试**：可以。Playwright 加载插件，打开一个在无手势时调用 getUserMedia 的测试页，用 `--autoplay-policy=document-user-activation-required` 强制自动播放策略，断言返回轨道有声音（用 WebAudio 分析 RMS）或者返回的是原始轨道。

### P1-13 口音校准中途离开页面，麦克风不释放，内存持续增长
- **平台**：macOS、Windows（桌面主窗口）

## P2

### P2-1 插件接管后，会议麦克风音质下降
- **平台**：Chrome
- **位置**：`extension/src/page-mic.ts:41`（`new AudioContext({latencyHint:'interactive'})` 没有指定 sampleRate）。
- **问题**：AudioContext 默认采用**当前默认输出设备**的采样率。默认输出是蓝牙耳机的 Hands-Free 端点（16 kHz 甚至 8 kHz）时，整条麦克风链路被降采样，对方在 Meet/Teams 里听到闷闷的声音，即使没开同传也一样。默认输出设备切换时也可能出现爆音或短暂中断。
- **建议修法**：使用 `new AudioContext({ sampleRate: real.getSettings().sampleRate || 48000 })`，或者按 P1-12 的建议在非同传状态下不经过 WebAudio。
- **能否自动测试**：可以。Playwright 断言 `ctx.sampleRate` 等于真实轨道的采样率。

### P2-2 插件内容脚本的匹配范围过宽
- **平台**：Chrome
- **位置**：`extension/manifest.json:61-74,83-96`。`https://*.feishu.cn/*` 覆盖了飞书文档、知识库、邮箱、妙记、后台，`*.zoom.us/*`、`*.webex.com/*` 覆盖了整站；两个脚本都是 `all_frames:true`、`document_start`。
- **影响**：
  - 飞书文档或妙记的录音、飞书网页版语音消息等也会走 P1-12 的接管逻辑。
  - `bridge.js` 在每个 frame 加载时都会发一次 `runtime.sendMessage({type:'bridgeReady'})` 唤醒 service worker（`bridge.ts:93-100`），这是额外开销。
  - 和其他同样在 MAIN world 包装 getUserMedia 的扩展（降噪、虚拟背景、会议记录类，如 Krisp / Tactiq / Otter）会叠加包装，效果取决于注入顺序。
- **建议修法**：收窄到会议路径，例如 `https://vc.feishu.cn/*`、`https://app.zoom.us/wc/*`、`https://*.zoom.us/wc/*`、`https://meet.google.com/*`、Teams 的会议路径等。
- **能否自动测试**：可以，用 manifest 静态检查。

### P2-3 插件用 `window.postMessage(…, '*')` 每秒约 12 次广播麦克风 PCM
- **平台**：Chrome
- **位置**：`page-mic.ts:37,93-98`。
- **影响**：会议页面自己的 `message` 监听器（以及页面里其他扩展的内容脚本）每秒收到约 12 条带 base64 PCM 的消息。有的站点会对每条消息 `JSON.parse` 或打日志，带来性能开销和报错；第三方脚本也能拿到用户的麦克风音频（隐私问题）。

- **能否自动测试**：可以。Playwright 在页面里监听 `message` 并计数。

### P2-4 插件 tabCapture 和其他软件的冲突
- **平台**：Chrome
- **位置**：
  - `extension/src/background.ts:66`：`tabCapture.getMediaStreamId`。
  - `extension/src/offscreen.ts:250-262`：在 offscreen 文档里用 `ctx.destination` 播放原声，走系统默认输出。
- **问题和影响**：
  1. 同一个标签页同时只能被一个扩展捕获。本插件运行时，Loom、Screencastify、Tactiq、Otter 等录制或转写扩展无法捕获该会议标签页；反过来，如果它们先捕获了，本插件就静默地拿不到会议声音（只有 `console.warn`）。
  2. 被捕获的标签页原声改由 offscreen 页面从**系统默认输出**播放，会忽略用户在 Meet/Teams 里选的扬声器（`setSinkId`）。比如用户在会议里选了耳机、系统默认是外放，开同传后对方的声音变成外放，可能造成回声和隐私泄露。

- **能否自动测试**：部分可以。第 2 点可以用 Playwright 断言 offscreen 的 `ctx.sinkId` 跟随页面设置。第 1 点要装两个扩展手动测。

### P2-5 插件接管时，克隆的轨道不会关掉真实麦克风
- **平台**：Chrome
- **位置**：`page-mic.ts:108-115`：只改写了 `out.stop`。
- **影响**：如果会议页对返回的轨道 `clone()` 后只 stop 克隆的那条，真实麦克风 `real` 永远不会被 stop。会议结束后标签页的录音红点和系统麦克风指示灯可能一直亮，蓝牙耳机停留在 HFP 模式。

### P2-8 Windows 常驻 PowerShell 进程
- **平台**：Windows
- **位置**：
  - `src/main/providers/system-tts-args.ts:2`：`-ExecutionPolicy Bypass -Command -`。
  - `windows-speech-host.ts:41`：`[System.Convert]::FromBase64String(…)`。
  - `system-tts.ts:253`：模块级单例 `sharedHost`，第一次会议后常驻到应用退出，从不 dispose。
  - `virtual-audio.ts:104`：安装驱动时也用 `-ExecutionPolicy Bypass`。
- **影响**：
  - 隐藏、长期运行、从 stdin 读取 base64 载荷的 `powershell.exe -ExecutionPolicy Bypass` 正是 EDR 规则（Defender for Endpoint 的 ASR "潜在混淆脚本"、CrowdStrike、SentinelOne）重点关注的形态。公司电脑上可能被拦截、隔离，或者给 IT 发告警（需在这类机器上验证）。
  - AppLocker/WDAC 强制的"受限语言模式"下 `Add-Type` / `New-Object` 被禁止，系统语音整体失效。
  - 会议结束后进程仍占用约 60–100 MB。
  - 退出时会被 libuv 的作业对象（KILL_ON_JOB_CLOSE）结束，并且 stdin 关闭后也会退出，**不会残留进程**（这一点没有问题）。
- **建议修法**：
  - 去掉 `-ExecutionPolicy Bypass`。`-Command -` 不受执行策略限制，这个参数没有必要。
  - 不用 base64：job 写成临时 JSON 文件（文本本来就写在 textFile 里了）。
  - 会议结束时 `sharedHost.dispose()`。
  - 检测到受限语言模式（`$ExecutionContext.SessionState.LanguageMode`）时给出明确提示，改用云端语音。
- **能否自动测试**：部分可以。单元测试断言参数里没有 Bypass 和 FromBase64String、会议结束会 dispose。EDR 的反应需要人工验证。

### P2-10 端口问题
- **平台**：Windows、macOS
- **位置**：

### P2-12 手机端的几处资源泄漏和静默失败

- **VB-CABLE 许可条款**：VB-CABLE 包里 `readme.txt` 写着 "It is not allowed to integrate the VB-CABLE package in another software installation procedure without Author agreement."，而本应用会下载它并用 `-h` 隐藏界面静默安装（`virtual-audio.ts:118`），用户看不到它的许可说明和"捐赠软件"说明。建议征得 VB-Audio 同意，或者改为打开官方安装界面（去掉 `-h`）让用户自己点 Install。
- **鸿蒙 4 的纯净模式**：默认禁止安装应用市场以外的 APK，用公开 community keystore 签名的 APK 还可能被标为"风险应用"。官网和引导里应写明关闭纯净模式的步骤。

## 逐项回答任务清单

1. **音频**
   - 默认设备：本应用代码**从不修改**系统默认设备（没有 IPolicyConfig、SwitchAudioSource、`pactl set-default-*`）。但 VB-CABLE 的安装会导致默认设备被换（P0-1）；BlackHole 不会改默认设备，只是本应用加的 coreaudiod 重启会断音（P1-2）。
   - 采集释放：会议（`engine.ts:362-380`）、试音（`engine.ts:382-400`）、声音复刻样本（`voice-sample.ts:42-46` 的 finally）、设备探测（`api.ts:43-44`）都会释放；口音校准中途离开页面不会释放（P1-13）。
   - 系统声音采集：视频轨道拿到后立即 stop，音频轨道在会议结束时 stop。macOS 上会议期间菜单栏一直有录屏/录音指示（预期行为），macOS 15 会周期性地再次征求同意（P2-13）。
   - 回声消除：Chromium 的 AEC 只处理本进程的采集流，以本进程的播放作为参考，不影响其他软件。iOS Safari 上打开麦克风会让声音走听筒（代码已经通过 2 秒后关麦缓解）。mac 上是否使用系统的 VoiceProcessingIO 并压低其他软件的声音，没有查到权威资料，**建议实机确认**（开会时用 Music 播放并观察音量）。
2. **CPU / 内存**：见 P1-5。空闲时在托盘：主进程只有启动 8 秒后的一次更新检查，`levels` 定时器只在会议中运行（`engine.ts:182`），设备变化靠事件（`api.ts:54`），没有发现轮询。会议期间隐藏的主窗口仍在渲染（P2-11）。
3. **端口**：桥接只监听 127.0.0.1:47811，不会触发防火墙，但被占用时静默失败（P2-10）。房间监听 0.0.0.0:47800（`schema.ts`），被占用时回退到随机端口，但会触发防火墙（P1-6），EACCES 不回退，失败后状态不回滚（P2-10）。
4. **Windows**：
   - 悬浮窗层级和遮挡见 P1-1，抢焦点见 P2-7。
   - 显示悬浮窗不抢焦点（`showInactive`）。主窗口只在启动、托盘点击、第二个实例启动时获得焦点。
   - 没有开机自启、文件关联、协议注册（`mi-app` 只在进程内用 `registerSchemesAsPrivileged`，见 `index.ts:60-64`）。
   - PowerShell 进程退出时不残留，但运行期间常驻且有安全软件风险（P2-8）。
   - NSIS 安装包按用户/按机器二选一、创建快捷方式，没有其他副作用；卸载会留下大量文件（P2-16），模型放在 Roaming（P1-8）。
5. **macOS**：
   - 权限：开会时请求麦克风（`index.ts:340`）；屏幕和系统声音在使用系统声音模式或录屏时请求；ad-hoc 签名导致升级后权限失效（P1-7）。
   - Dock 图标消失（P2-6），窗口层级（P1-1）。
   - `say` 进程和临时文件没有问题（P2-19）。
   - 没有登录项。
6. **Chrome 插件**：
   - 权限：`storage`、`tabCapture`、`offscreen`、`declarativeNetRequestWithHostAccess`。host 权限只列了具体的 API 域名和 localhost，`https://*/*` 是可选权限，范围合理。DNR 只改插件自己的 WebSocket 请求头（`browser-context.ts:83-96`），**不影响其他网站**。
   - 内容脚本只注入 12 个会议域名，不是所有网页，但范围偏宽（P2-2）。在这些站点上**一直接管 getUserMedia**（P1-12），有音质损失（P2-1）和 postMessage 广播（P2-3）。
   - 和其他扩展的冲突见 P2-2、P2-4。
7. **手机**：
   - 安卓 App 权限是 INTERNET、RECORD_AUDIO、MODIFY_AUDIO_SETTINGS，属于合理范围；切后台问题见 P1-9；没有使用 WakeLock，只用 `FLAG_KEEP_SCREEN_ON`，只在前台生效，停止时清除。
   - iOS：WSS 见 P0-2，静音拨片见 P1-10，AudioWorklet 需要 iOS 14.5 以上（P2-12），wakeLock 需要 iOS 16.4 以上且没有正确管理（P2-12）。
   - 自动播放：房间页在点击里解锁音频，安卓 App 设置了 `setMediaPlaybackRequiresUserGesture(false)`，都没有问题。
   - 手机端不使用 SharedArrayBuffer、speechSynthesis、MediaRecorder；WebAssembly 只在安卓 App 的离线翻译里使用，非线程版、不需要 SIMD。
   - 会静默失败的情况：iOS 的 WSS、静音拨片、微信扫码、安卓老 WebView 白屏、鸿蒙 NEXT 官网识别错误。
8. **其他**：P1-3、P1-4、P2-9、P2-14、P2-15、P2-17。

## 需要真机验证的清单（建议放进发布前检查）

1. Windows 10 和 11 干净系统：一键装 VB-CABLE 后，检查默认播放、录音、通信设备是否改变，Teams 是否还有声音。
2. iPhone（iOS 17 / 18 / 26）：局域网链接加入房间，WebSocket 能否连上；静音拨片打开时能否听到译音。
3. 微信（iOS 和安卓）扫局域网二维码、公网二维码，分别看结果。
4. 鸿蒙 NEXT 浏览器：打开官网、局域网房间（自签名证书能否继续访问、wss 能否连上）。
5. 安卓 15 设备和鸿蒙 4 设备：切后台后 `dumpsys audio` 的模式和录音客户端；顶部和底部是否被系统栏遮挡。
6. macOS：从旧版覆盖升级后，"系统声音"模式是否还能采到声音；开会时其他软件（Music）的音量是否被压低。
7. Chrome：装上插件后，从日历链接进入 Meet/Teams，不点击页面，对方能否听到；输出是蓝牙 HFP 时的麦克风音质。
8. 装有 Defender for Endpoint / CrowdStrike 的公司 Windows：系统语音、驱动安装、cloudflared 是否被拦截。
