## 详细说明

### 1. [P0] Windows / Linux：API Key 重启后全部丢失，再保存会永久覆盖
- **模块**：src/main/stores/secret-store.ts、src/main/index.ts
- **位置**：`src/main/index.ts:101` 在模块顶层执行 `const secrets = new SecretStore(dataDir, safeStorage)`，早于 `app.whenReady()`（:1013）。`src/main/stores/secret-store.ts:28-37` 的 `load()` 逻辑是：`if (raw.enc && this.safe.isEncryptionAvailable()) …decrypt`，否则 `if (raw.plain)`，否则 `return {}`。
- **问题**：Electron 45 自带的 `electron.d.ts` 写明 isEncryptionAvailable：「On Linux, returns true if the app has emitted the ready event…; On Windows, returns true once the app has emitted the ready event」。所以在 Windows 和 Linux（有 keyring）上，构造时 `load()` 读到 `{enc: …}` 但判断加密不可用，返回 `{}`：所有 Key 显示「未保存」，开会报「请先填写 Key」。用户补填其中一个 Key 时（已经 ready，加密可用），`save()` 把只含这一个 Key 的 cache 加密后覆盖 secrets.json，其他 Key（大模型、DeepL、Azure 翻译等）**永久丢失**。macOS 上 Keychain 在 ready 前可用，所以开发机上看不到这个问题。现有单测 `tests/main/session.test.ts:43-49` 用的假 safeStorage 一直可用，覆盖不到。
- **复现**：Windows 上填阿里云百炼 Key 和大模型 Key，保存，退出重启：设置页两个都显示没填。再填百炼 Key，重启：大模型 Key 找不回来。
- **建议修法**：在 `app.whenReady()` 之后再构造 SecretStore，或者首次 get/all/status 时再懒加载（IPC 都在 ready 之后才有）。`load()` 解不开 enc 时要记录 `unreadable=true`：此时 `save()` 不能直接覆盖，先把旧文件备份成 `.bak`，或拒绝写入并提示。
- **建议的测试**：用假 safeStorage，先让 `isEncryptionAvailable` 返回 false、之后返回 true。断言 ready 之后能读到旧 Key；断言「解不开时再 set 一个 Key」不会丢掉其他 Key（或者会保留 .bak）。

### 2. [P0] 现场房间：参会者停顿超过 60 秒再说话，会覆盖自己之前的句子（已复现）
- **模块**：src/main/room/room-host.ts、src/core/pipeline/pipeline.ts
- **位置**：room-host.ts:434-439，停说 `idlePipelineMs`（默认 60 秒）后执行 `p.pipeline = null; old.stop()`；:441-443 再说话时 `makePipeline(me)` 新建 pipeline；:478 `idPrefix: \`room-${p.id}\`` 不变；pipeline.ts:296 句子 id 是 `${idPrefix}-${++this.seq}`，seq 每个新 pipeline 都从 0 开始。
- **问题**：新 pipeline 产出的 `room-ab12cd-1`、`-2`… 和之前的句子 id 相同。`Transcript.upsert` 和 transcript.jsonl 都是「同一 id 以最后一条为准」，所以会议记录里这个人之前的句子被覆盖、丢失。桌面房间页和每台手机的列表也按 id 替换，前面的气泡消失。
- **复现**：scratchpad/s/room-id.mts（idlePipelineMs=50）。第一次说话后记录是 `room-57869c-1: 大家好…`；停说、pipeline 释放后再说话，记录只剩 `room-57869c-1: 我们今天主要讨论…`，第一句没了。真实场景：手机端停 1 分钟以上再按住说话。
- **建议修法**：序号不随 pipeline 重来，在 Participant 上保存 seq；或者每次 makePipeline 用新前缀，例如 `room-${p.id}-${n}`；或者给 DirectionPipeline 增加 `startSeq` 选项。
- **建议的测试**：在 tests/main/room.test.ts 的「room resources」用例里，两次说话之间等 pipeline 释放，断言 `session.segments()` 有 2 条且 id 不同。

### 3. [P1] 会后自动学习会把单字纠错（的→得、在→再）变成全局规则（已复现）
- **模块**：src/core/profile/review.ts、src/main/index.ts、src/core/profile/profile.ts
- **位置**：review.ts:86-88 只要求长度不超过 20、原句里包含、`soundsAlike`，**不限制最短长度**。index.ts:718-732 `reviewMeeting` 对每条建议直接 `addCorrections(…, 'review')`、`split(heard).join(meant)`，并设 `decision='accepted'`（自动采纳，不等用户确认）。profile.ts:130-133 对中文做全文 `split(heard).join(meant)`。
- **问题**：提示词让模型找「同音或近音误识别」，模型很容易给出 的/得/地、在/再 这类单字「纠错」，而 soundsAlike 判它们同音。规则一旦写进口音档案，**以后每场会议识别出的每个「的」都会被改成「得」**，翻译跟着错。`learnFromEdit` 里明确防了单字（learn.ts:160-167 的注释：so a single character is never rewritten everywhere），review 这条路径没有防。另外 `split().join()` 会把同一句里本来正确的「的」也一起改掉。撤销（index.ts:419 `indexOf(item.meant)`）只恢复第一个出现的位置，撤不干净。
- **复现**：scratchpad/s/review.mts 用假 LLM 返回 `{"heard":"的","meant":"得"}` 和 `{"heard":"在","meant":"再"}`，两条都通过过滤。把它们加进档案后，`applyCorrections('我在公司的会议室等你的消息')` 得到 `我再公司得会议室等你得消息`。
- **建议修法**：review 对中文要求 heard 和 meant 都至少 2 个汉字（可沿用 learnFromEdit 的扩词策略），并排除常见虚词。只替换模型指出的那一处，不要全句 split/join。撤销按记录的位置精确恢复。也可以考虑自动采纳的规则只对当场会议生效，用户确认后再写进档案。
- **建议的测试**：用假 LLM 返回单字建议，断言 `reviewMeeting` 的结果里没有它们；同一句里两个「的」只改指出的那个；undo 恢复全部被改的位置。

### 4. [P1] 现场房间：任一手机不回 close 帧时，关闭房间卡 30 秒（已复现）
- **模块**：src/main/room/room-host.ts
- **位置**：:256 `p.ws.close(1001)`，这是优雅关闭，要等对端回 close 帧，ws 库默认 closeTimeout 是 30 秒；:267 `await new Promise(r => this.server!.close(() => r()))`，http server.close 要等所有连接（包括升级后的 WebSocket）都断开。还没 join 的 pending socket 根本没有被主动关闭。`session.stop()` 排在这之后（:270-272）。
- **问题**：手机锁屏或浏览器进后台时，TCP 连接还在，但页面不处理 close 帧。主持人点「关闭房间」或「结束会议」后按钮转圈 30 秒（有未加入的 pending socket 时更久，加上 join 超时 15 秒）。这段时间主持人麦克风还在翻译，转写文件没有落盘；用户以为卡死去强退，会丢掉 transcript.md/srt 和 endedAt。
- **复现**：scratchpad/s/roomstop.mts 让手机端 `_socket.pause()` 模拟锁屏，结果 `room.stop took 30.2 s`。
- **建议修法**：发出 ended 和 close 之后约 1 秒对没关掉的 socket 调 `terminate()`；对 `wss.clients` 全部处理，覆盖 pending；或者调 `server.closeAllConnections()`。先 `session.stop()`，再等网络关闭。
- **建议的测试**：照上面的脚本写成单测，断言 `room.stop()` 在 3 秒内完成，且 `session.active === false`。

### 5. [P1] 插件：storage.local 写满后，结束会议时会议丢失，插件卡在「stopping」
- **模块**：extension/src/background.ts
- **位置**：:87 先 `setState({status:'stopping'})`；:98-99 `finish()` 里 `if (meeting) await saveMeeting(meeting)` 没有 try；:114 `chrome.storage.local.set({meetings: list.slice(0, 30)})`。manifest.json 没有 `unlimitedStorage`，storage.local 上限 10MB，按 UTF-8 字节计，中文每字 3 字节。
- **问题**：只按条数（30 场）限制，不按体积限制。一小时双向会议的 segments 大约 0.3–0.5MB，加上纪要，累计二十来场长会议就会超额。超额时 `set` 抛 QUOTA_BYTES，`finish()` 后半段（engine-stop、关闭 offscreen、清 DNR 规则、`setState(IDLE)`）全部跳过：这场会议没保存，状态永远停在 `stopping`。之后 `start()` 遇到 stopping 直接返回（:56），只能重启浏览器或重载插件。options 页保存纪要（options.ts:452-453）也会遇到同样的超额。
- **复现**：手动往 storage.local.meetings 塞约 10MB 数据（或连开多场长会议），然后开始、结束一场：弹窗一直显示「正在结束」，会议列表里没有这场。
- **建议修法**：`finish()` 用 try/finally 保证复位状态。保存前按体积裁剪旧会议（`getBytesInUse`），失败时再删最旧的重试，仍失败就提示用户导出。或者申请 `unlimitedStorage`，或者把会议存进 IndexedDB。
- **建议的测试**：mock `chrome.storage.local.set` 抛 quota 错误，断言 stop 后状态回到 idle，并有错误提示；裁剪逻辑按体积留下最新的会议。

### 6. [P1] 手机版：暂停后再开始，之前的对话被覆盖、顺序打乱
- **模块**：mobile/src/app.ts
- **位置**：:129 `const segs = new Map()` 是全局的，只有「清空」按钮（:360，且只在停止时显示）会清；:156 `idPrefix: 'zh' | 'fx'` 固定；:150 `t0 = Date.now()` 每次 start 重设；排序按 `start`（:327）。
- **问题**：按钮写的是「暂停」，用户自然会暂停再继续。第二段对话的 `zh-1`、`fx-1`… 覆盖第一段同 id 的句子，而且 start 时间从 0 重新计，新旧句子按时间交错排列。屏幕上的对话内容是错的，前面的句子悄悄没了，对话只存在内存里，等于丢失。

- **建议的测试**：对 app.ts 的 start/stop 用 mock providers 跑两段，断言 segs 数量等于两段之和，并按时间单调排列。

### 7. [P1] 纪要 JSON 校验过严，一个字段类型不对整份纪要就失败（已复现）
- **模块**：src/core/session/summary.ts
- **位置**：:18 `start: z.number()`；:10 `evidence: z.array(z.string())`；:30 `owner: z.string().nullable()`；`parseSummary` 只把 title/summary/text 的纯字符串转成双语对象，其他字段不做容错。:58 给模型看的行格式是 `[L3 01:15 我方]`，:83 却要求 `"start":seconds`。
- **问题**：模型照着行里的样子返回 `"start":"01:15"`，或者把 evidence 写成 `"L1"` 字符串（免费模型很常见），zod 就抛错。重试一次还是一样，最后 toast 显示「纪要生成失败：[ { "expected": "number", "code": "invalid_type", … } ]」：功能失效，而且提示看不懂。
- **复现**：scratchpad/s/sum.mts，`start:'01:15'` 和 `evidence:'L1'` 两种情况都报 zod 错。
- **建议修法**：用 `z.preprocess` 或 `z.coerce` 容错：把 "mm:ss" 或 "h:mm:ss" 转成秒，字符串 evidence 包成数组，非字符串 owner/due 转成 null。单个 topic 或 todo 解析失败时丢掉那一条，不要整份失败。错误提示改成中文。
- **建议的测试**：在 summary 测试里加这几种畸形 JSON，断言能解析出合理结果。

### 8. [P1] 术语表页：「常被听成」打不出第二个别名，也打不出多词西语别名（已复现）
- **模块**：src/renderer/src/pages/Glossary.tsx
- **位置**：:8 `split = s => s.split(/[;；,，、]/).map(x => x.trim()).filter(Boolean)`；:168、:172、:174 输入框是受控的：`value={aliases.join('；')}`，`onChange={… split(value)}`。
- **问题**：每敲一个键都 split、trim、filter 一遍，再 join 回去。末尾的分隔符「；」和末尾空格会被立刻去掉。实际效果：①敲完「报价」再敲「；」，分号马上消失，接着敲出来的是「报价报价单」，**无法逐字输入第二个别名**（中文输入法同样如此）；②西语或英语别名敲到 `plazo␠` 时空格被吃掉，接着变成 `plazode`，**打不出多词别名**。只有一次性粘贴才行。插件 options 页用的是非受控 input（options.ts:369-375），没有这个问题。
- **复现**：node 模拟 round-trip：`"报价；" -> "报价"`，`"plazo " -> "plazo"`。在术语表页实际输入也能复现。
- **建议修法**：这一列用本地字符串 state 保存原文，onBlur 或保存时再 split；或者改成非受控 input 加 defaultValue。
- **建议的测试**：Playwright 用例：在「常被听成」逐字输入 `报价；报价单` 和 `plazo de entrega`，保存后断言别名数组正确。

### 9. [P2] 插件免费版：热词放在 URL 里，超过 16KB 被拒，报错却是「连接不上桌面客户端」（已复现）
- **模块**：src/core/bridge/desktop.ts、src/main/bridge/desktop-bridge.ts
- **位置**：desktop.ts:82 `ws://…/asr?lang=…&hw=${encodeURIComponent(JSON.stringify(hotwords.slice(0,200)))}`；desktop-bridge.ts:60 用默认 `createServer`，Node 默认 maxHeaderSize 是 16KB。
- **问题**：中文 URL 编码每字 9 个字符，200 个较长的术语（加上口音档案的 meant，最长 60 字）就会超过 16KB，服务端返回 431，客户端 onerror 显示 NOT_RUNNING「连接不上本机的会议同传助手」，误导用户。桌面端本机识别本来就不支持热词（client.ts 注释 hot words are not supported），这些热词传过去也没用。
- **复现**：scratchpad/s/bridge.mts，100 个热词（URL 10KB）能连上；200 个（URL 20KB）返回 `HTTP 431`。
- **建议修法**：不再发 hw，或者改成连上之后用第一条文本消息发送，并限制总长度。客户端区分「连不上」和「被拒（4xx）」两种情况。
- **建议的测试**：desktop-bridge 测试里用 200 个长热词连接，断言能 ready。
